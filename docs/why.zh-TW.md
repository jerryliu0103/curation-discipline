# 為什麼有這個東西

## 問題的形狀

多數談 AI 輔助資料工作的文章，講的是怎麼讓代理產出好東西。這個 plugin 講的是另外
一半：**你怎麼知道它真的產出了。**

這兩件事不一樣，而且第二件更難，因為資料流水線有一個多數軟體沒有的性質。一般程式寫
錯了通常會當掉；**資料流水線寫錯了通常會跑完**、回報成功，然後交給你一份微妙地不完整
的資料集——而那些不完整的列，跟完整的列長得一模一樣。

LLM 代理讓這件事更尖銳，具體有三點：

**輸入缺了它會生出像樣的輸出。** 跟資料庫要一筆不存在的資料，你得到零列；跟代理要，
你可能得到一個自信、格式正確、完全虛構的答案，然後它躺在你的資料集裡，跟其他每一列
看起來都一樣。

**它會改寫，不會重複。** 同一份來源送兩次，決定性的匯入程式會產生位元組相同的文字，
你可以用雜湊抓到。代理每次產生的字都不一樣。**所有靠文字相似度做的去重在這裡都會
失效**——不是偶爾失效，是結構性地失效。

**它遵守指示遵守得夠好，好到你不再檢查。** 這是最危險的一點。一個正確遵守規則四十次
的代理，已經訓練你不去驗第四十一次，而第四十一次不會有任何地方看起來不一樣。

## 材料從哪裡來

一個繁體中文的食材與風味搭配資料庫。一個人、Claude Code、幾個月、數千筆逐筆標註來源
的策展資料。正本是跑在家用伺服器上的 Postgres，對外有一個帶三層存取控制的唯讀檢視，
另外有一個單向寫進筆記軟體的鏡像，讓人可以用瀏覽的方式看資料。

領域本身不重要，也已經拿掉了。留下來的是機制，更重要的是事故。

## 為什麼事故才是有價值的部分

流水線的形狀——蒐集、驗證、核准、寫入——不是什麼發現。任何人想十分鐘都會走到這個
結論。你自己大概也寫得出來。

**你沒辦法從第一原理推導出來的，是它會用哪些方式安靜地失敗。** 那個清單只能靠跑幾個月
再一個一個發現。舉幾個：

- 一次**其實不是試跑的試跑**。SQL 檔在經過幾層工具轉換時掉了一個反斜線，交易從來沒
  開始，22 個敘述逐句自動提交。唯一的警訊是結尾一行「目前沒有進行中的交易」，夾在
  一堆看起來很正常的驗收輸出裡。
- 一個印出來了、但什麼都沒回捲的 `ROLLBACK`。那個字一定會印。
- 一次 schema 變更：從「一個項目一列」改成「多個來源各一列」。所有下游用 `LEFT JOIN`
  預期取一列的查詢開始取到多列，528 列變成 550 列。沒有任何錯誤，鏡像那端安靜地長出
  重複頁面。
- 一支 `PreToolUse` guard 在非 UTF-8 的主控台上丟 `UnicodeEncodeError`，以非 0 離開
  且沒有輸出任何決定，於是**停止攔截任何東西**——而它看起來跟一支正常運作的 guard
  完全一樣。
- 一支專門為了防止某類重複而寫的解析器，在一個沒合併的分支上躺了三週。那三週裡，
  「一律要用這支解析器」這條規則等於不存在。等到終於合併時，它引用的欄位早就被移除了。
- 一個萃取代理認出某段話含有三類內容，產出了兩類，第三類掉了。每一份清單內部都自洽。
  是人直接問「那一段你是怎麼處理的」才發現。

完整清單與各自的抓法：`silent-failure-hunting` skill。

## 三個就算什麼都不裝也值得帶走的想法

### 1. 用結構強制，不要用拜託

「代理絕不可碰某個資料源」這條規則被忽略了一個月——查核時五個代理檔全都在違反它。
沒有人粗心。**違反時沒有任何東西會失敗**，所以完全沒有回饋。

一條沒有失敗模式的規則只是一個偏好。你想要它被遵守，就得把它掛在一個會停下來的東西上。

而當你做了那個 guard：**要用對抗的方式測它。** 餵它該擋的東西，然後斷言它擋了。這個
plugin 裡的 `test_hooks.py` 在第一次執行就抓到真實錯誤——剝除引號內容把 SQL 本身剝掉
了，於是 guard 一邊放行所有寫入一邊回報成功。那個錯誤只存活了一次測試，**這就是為什麼
要連測試一起附上**。

### 2. 比對來源座標，不要比對文字

你沒辦法靠比對文字抓到重複匯入，因為文字每次都不一樣。記下它從哪裡來——哪份文件的
哪個位置、哪個項目的哪個來源——然後比對那個。光是這一個改變就消掉一整類重複。

**兩個座標，不是一個**：誰說的，以及你哪一天拿到的。一旦你接受多個來源是並存而不是
互相覆蓋，「這幾筆裡哪一筆是現行的」就變成一個真實的問題，而沒有日期就無法回答。

### 3. 要求丟棄清單

要求每一個萃取代理回報它**丟掉了什麼**、為什麼丟、在哪裡丟的。

這在你看到它的用途之前都像是多餘的工。如果代理把有價值的東西誤判成雜訊，產出看起來
會完美無缺——少掉的那則就只是不在那裡，而且沒有任何跡象顯示它曾經在。**丟棄清單是
那個判斷唯一留下的紀錄。**

**空的丟棄清單是紅旗，不是乾淨。** 一批什麼都沒丟的資料，幾乎可以確定是代理根本沒
考慮過要丟。

## 刻意沒有放進來的東西

**任何領域專屬的內容。** 那些分類裁決——某個邊界項目該歸哪一類、一個在兩份來源裡指
兩種東西的名字該怎麼處理——不會泛化。它們是原專案裡最貴的部分，而且對你一文不值，
因為你的領域難的地方跟這裡不一樣。

**權利管理層。** `principle-extractor` 處理的是「把方法與表達分開」，那是方法問題。
要對你不擁有的材料建一套**可稽核**的流程——依可公開性分級、改寫與原文成對存放、在
資料庫／應用層／API 三層強制存取控制——是另一個大得多的設計問題，不是一個代理定義
就能解決的。**不要把這個 plugin 讀成「裝了就可以安全公開你的語料」。**

**基礎設施。** 備份排程、同步腳本、排程工作。那些占了原專案自動化的大半，而且一條都
搬不走——全是路徑與機器名稱。

## 貢獻

這份清單靠回報長大。如果你踩到一個不會報錯的失敗，開一個 issue：發生了什麼、
是什麼讓它安靜、現在靠什麼抓。**第三項才是讓它值得被收進來的原因。**
